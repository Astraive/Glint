### Added

- Versioned, typed local IPC with subscription snapshots (`[COR-003]`, [ADR 0010](docs/adr/0010-interprocess-for-local-ipc.md)): new `glint-ipc` crate over the portable `interprocess` crate (a random-suffix named pipe with an owner-only DACL on Windows, a `0600` socket in the data root on Unix, recorded in `<data>/ipc.endpoint`). Length-prefixed JSON frames (64 KiB requests, 1 MiB responses), `hello`/`welcome` version negotiation (API version 1), request envelopes with `request_id` and `api_version`, a closed set of typed requests (`ping`, `get-status`, `get-snapshot`, `get-state`, `get-config`, `get-capabilities`, `get-theme`, `subscribe`, `shutdown`; anything else is `GLINT_IPC_UNKNOWN_REQUEST`) and typed errors with stable `GLINT_IPC_*` codes that keep unsupported, permission-denied, unavailable, timeout and failure apart. Subscriptions start from the current snapshot and stream ordered deltas with sequence numbers, heartbeats, a resync snapshot for lagging subscribers and `closed`; the client library refuses gaps and reconnects to the current snapshot. `glint-core` `CoreIpc` publishes the runtime's state (reads never reach the daemon) and an IPC `shutdown` takes the clean shutdown path; `glint-daemon` serves it once ready (`ipc listening <endpoint>`, exit 1 if the endpoint cannot be served) and a second launch prints `already-running pid=<pid> ipc=<state>`. Golden JSON fixtures in `crates/glint-ipc/tests/fixtures/`; an end-to-end test drives the real binary. `recvmsg` and `doctest-file` (0BSD) get per-crate license exceptions pending maintainer approval. Per-user peer checks and the cross-user test remain SEC-002's; threat-model rows B7.1, B7.2, B7.3, B7.5 and B7.7 updated. The CLI does not use IPC yet (CLI-006).
- Per-user single instance and clean shutdown (`[COR-002]`): the core takes an exclusive lock on `<data>/instance.lock` (released by the OS on any exit) before opening the database and records its pid in `instance.owner`; a second `glint-daemon` stops with `GLINT_CORE_ALREADY_RUNNING`, prints `already-running pid=<pid>` and exits 9 without touching state; `probe_instance` detects a running core. Shutdown closes surfaces and releases work-area reservations, flushes and closes state, then releases the lock, running every step and reporting each failure; `ShutdownSignal` and `Runtime::run_until` collect shutdown triggers. Console Ctrl+C and `WM_ENDSESSION` hooks wait for the native host crates. Threat-model rows B7.7 (new) and B9.1 updated.
- Single-process core runtime (`[COR-001]`, ADR 0001): `glint-daemon` (state authority and only writer of profile and package state: storage and installer recovery, config resolution with rejected user config reported, capability discovery through an adapter, active theme through the capability gate or the embedded default theme with a typed fallback reason; `GLINT_DAEMON_*` codes), `glint-shell` (surface presentation through a `SurfaceBackend`, reservations released on close, a headless backend that never touches the OS shell; `GLINT_SHELL_*` codes; no storage dependency) and `glint-core` (`Runtime` with typed boot stages, lifecycle states and events, `GLINT_CORE_WARN_*` warnings, stage-named `GLINT_CORE_*` errors, ordered shutdown). The `glint-daemon` binary (`apps/daemon`) hosts it headless. Trust trade-off and split conditions in [docs/architecture/core-runtime.md](docs/architecture/core-runtime.md).
- Offline theme workflow in the `glint` CLI (`[CLI-002]`): `glint theme import PATH` (stages a `.glint` or theme directory through the strict reader and installs it without activating; a rejected package leaves the inventory and active theme unchanged), `theme list`, `theme export [-o PATH] ID` (the PKG-005 export), `theme remove ID`, `theme use ID|default` and `glint safe-mode` (activates the bundled default theme in a separate `safe-mode` profile), all on Glint state only under `GLINT_HOME` or the OS directories, through new `glint-installer` operations (`BundledTheme`, `ensure_bundled`, `import`, `find`, `use_theme`, `safe_mode`; codes `GLINT_INSTALL_BUNDLED_INVALID`, `GLINT_INSTALL_RESERVED_ID`, `GLINT_INSTALL_AMBIGUOUS`). The default theme is packed deterministically by `apps/cli/build.rs` and embedded in the binary, so safe mode works with an empty store, a damaged store entry or a corrupt database, and the `official.default` ID cannot be shadowed by an import. The CLI output schema gains documented `$defs/data` shapes validated by the new `apps/cli/tests/cli_roundtrip.rs`; [docs/cli/reference.md](docs/cli/reference.md) updated. The interactive `glint theme` chooser stays unimplemented and unscheduled.
- Export of installed packages without private data (`[PKG-005]`): `glint-installer` `Installer::export` writes an installed release back to a `.glint` by re-packing only its extracted package tree with the new deterministic `glint-package` `export_package_tree` (no authoring exclusions, no timestamps, owners, extra fields or comments), after checking the stored archive against its digest, and reads the result back through the strict reader before moving it into place. Provenance (`install.record`, source paths, retrieval and install times), the state database, profiles, pins and grants are never included. A Glint-packed release exports byte-identically, so re-importing it is a no-op with the same digest; an archive from another ZIP tool exports to its canonical form, which stays stable across further export/re-import cycles. New codes `GLINT_INSTALL_STORE_CORRUPT`, `GLINT_INSTALL_EXPORT_FAILED` and `GLINT_INSTALL_EXPORT_DESTINATION_INVALID`; tests in `crates/glint-installer/tests/export.rs` scan the archive bytes and every extracted file for the Glint root, source path and user name.
- Semantic design token contract (`[THM-004]`): a closed registry of role-named tokens (`background.default`, `surface.raised`, `text.primary`, `focus.ring`, `panel.height`, typography, space, radius, elevation, motion) in `glint-schema` with `parse_tokens` for the *proposed* `tokens.json` v1 (dark and light colour schemes, closed value grammars, stable `GLINT_TOKENS_*` codes with JSON Pointers), Glint brand constants such as `Obsidian` refused as names (`GLINT_TOKENS_BRAND_NAME`), WCAG contrast requirements per scheme (`contrast_ratio`, `GLINT_TOKENS_LOW_CONTRAST`) and `TokenFile::to_css` for the `--glint-*` custom property mapping with `prefers-color-scheme`, `data-glint-scheme` and reduced-motion rules. New [`schemas/glint-tokens-v1.schema.json`](schemas/glint-tokens-v1.schema.json) and [docs/architecture/design-tokens.md](docs/architecture/design-tokens.md). The default theme's `theme/tokens.json` and fallback panel CSS now follow the contract (neutral greys in both schemes, no green); the provisional THM-001 token layout is replaced.
- Frozen v1 capability registry in `glint-platform` (`registry` module): 43 IDs across `surface.*`, `system.*`, `desktop.*`, `native.*` and `host.*`, each with read/write/present access, a sensitivity class, its integration effect and platform notes, published in [docs/spec/capabilities-v1.md](docs/spec/capabilities-v1.md) with the freeze rules and the process for adding IDs ([ADR 0009](docs/adr/0009-frozen-v1-capability-registry.md), Proposed). Unknown IDs fail closed at validation and at runtime: `glint-package` derives `known_capabilities` from the registry (`PROVIDER_CAPABILITIES` removed; `native.*`, `host.*`, `system.network.ssid`, `system.battery.read` and `system.power.source.read` are now accepted, nothing previously accepted is refused), the capability service refuses an adapter report with an unregistered ID (`adapter-failure`), snapshot lookups report `unknown-capability`, and the activation gate refuses a theme declaring an unregistered ID even as optional. `glint-surfaces` resolves catalog capabilities through the registry. Generated `packages/types/src/capabilities.ts` (closed `CapabilityId` union, now used by the surface types), drift-checked by `cargo test -p glint-platform --test registry` (`[CAP-005]`).
- Manifest references and static content restrictions in `glint-package` (reader and packer): every token, asset, layout and surface HTML entrypoint must be a regular file in the archive (a missing entrypoint is `GLINT_PACKAGE_MISSING_REFERENCED_FILE`); every surface is validated with `glint_surfaces::surface_definitions` and refused as `GLINT_PACKAGE_INVALID_SURFACE` carrying the `GLINT_SURFACE_*` code and JSON Pointer (`PackageError::surface_error`); SVG images with scripts, `foreignObject`, event handlers, `javascript:` URLs or entity declarations are refused as `GLINT_PACKAGE_ACTIVE_CONTENT`; the remote-reference scan also catches `/`- and quote-separated attributes, `<a ping>`, `background`/`imagesrcset`/`manifest` attributes, CSS `image-set()` and JS `WebSocket`/`EventSource`/`sendBeacon`/`SharedWorker`. Known capabilities are now derived from the surface catalog plus a provisional `PROVIDER_CAPABILITIES` list (`known_capabilities`, `is_known_capability`, replacing `KNOWN_CAPABILITIES`), so catalog capabilities such as `surface.dock` are accepted and unknown IDs stay refused until CAP-005 freezes the registry. `glint theme validate` reports `surfaceCode` and `pointer` for surface errors. New `references` fixture suite documented in [docs/security/package-fixtures.md](docs/security/package-fixtures.md) (`[PKG-004]`).
- `glint-surfaces` crate (no OS-specific dependency): the portable surface catalog (panel, dock, launcher, control-center, notification, notification-center, desktop, calendar, power-menu, workspace-switcher, window-switcher, volume-osd, brightness-osd, media-overlay and namespaced `custom:<namespace>.<name>` kinds) with required `surface.*` and optional provider capabilities, and a parser that validates each manifest surface's entrypoint (package-local `.html` only, never `file://` or remote pages) and its *proposed* `placement` and `behavior` objects into a `SurfaceDefinition`, with stable `GLINT_SURFACE_*` codes and JSON Pointers. The manifest surface object accepts an optional raw `behavior` object (JSON Schema, TypeScript validator and fixtures updated). `@glint/types` gains `src/surfaces.ts`, generated from the Rust catalog with a `cargo test` drift check. Specified in [docs/architecture/surfaces.md](docs/architecture/surfaces.md) (`[SRF-001]`).

- `glint-sources` `parse_theme_source`: a pure, network-free parser for theme source strings (`registry/package[@version]`, `https://…/repo.git` or `git+https://…` with the *proposed* `#ref:subpath` fragment, `https://….glint` artifact URLs, and local paths starting with `/`, `./`, `../`, `~/` or a drive). It refuses `file:`, `http:`, `ssh:`, `git:`, `ext::`, `javascript:` and every other scheme, SSH shorthand, leading `-`, credentials in URLs, IP-literal and local hosts, UNC and device paths, control and invisible characters, dot segments and encoded separators, ambiguous forms and input over 2048 bytes, with stable `GLINT_SOURCE_URL_*` codes; accepted URLs are canonicalized (`[SRC-002]`).

- Proposed `profile.json` v1 and `profile.lock` v1 formats ([profile format](docs/architecture/profile-format.md)): JSON Schemas under [schemas/](schemas/glint-profile-v1.schema.json), `glint-schema` parsers with stable `GLINT_PROFILE_*` codes, one theme version per profile, lock entries that must pin kind, id, exact version, canonical origin and SHA-256 digest, local-only flagging of private wallpaper files and machine-specific monitor keys for export, `verify_profile_lock`, and synthetic [profile fixtures](tests/profile-fixtures/README.md) (`[SCH-006]`).
- Proposed `config.toml` v1 application config and merge policy ([application config](docs/architecture/application-config.md)): read-only bundled defaults in [config/default.toml](config/default.toml), a [JSON Schema](schemas/glint-config-v1.schema.json), and `glint-schema` `parse_config_layer`/`resolve_config` with stable `GLINT_CONFIG_*` codes. User keys override defaults one by one and `[registries.<name>]` merge by name; user changes that weaken a security default are reported; settings requested by a package are never applied and are reported as ignored, so `allow_native_scripts`, `confirm_new_permissions` and `untrusted_network_default` cannot be weakened by a theme. Adds the `toml` crate (`[SCH-007]`).
- `glint` CLI skeleton: the *proposed* command tree (`doctor`, `status`, `safe-mode`, `theme ...`, `profile ...`, `registry ...`, `permissions list`) with argument checking, a schema-versioned `--json` envelope ([schemas/glint-cli-output-v1.schema.json](schemas/glint-cli-output-v1.schema.json)) and stable exit codes for usage, unsupported, invalid package, permission denied, missing daemon, not found and timeout; the interactive `glint theme` chooser is only offered on a terminal. `glint version` and `glint theme validate [PATH]` (package and manifest checks through `glint-sources`/`glint-package`) work; every other command fails with `GLINT_CLI_NOT_IMPLEMENTED` (exit 3) and never reports success. Documented in [docs/cli/reference.md](docs/cli/reference.md) (`[CLI-001]`).
- Bundled default theme [themes/default](themes/default/README.md) (`official.default`): a real `.glint` package with a v1 manifest that needs no capability, graphite and silver tokens, a static script-free panel surface, a preview image and the MIT licence, all repository-owned and offline; it packs deterministically and passes the same strict package reader as third-party themes (`cargo test -p glint-package --test default_theme`) (`[THM-001]`).
- `glint-storage` crate with OS-resolved paths: Glint's configuration, data and cache directories come from the platform base directories through `dirs` (Known Folders on Windows, XDG on Linux, Standard Directories on macOS; [ADR 0007](docs/adr/0007-dirs-for-os-path-resolution.md)), with only configuration in the Windows roaming profile; `GLINT_HOME` or an explicit root overrides all three for tests; relative overrides are refused, every derived file location stays inside the roots and no user name or home path is hardcoded (`[INS-001]`).
- `glint-storage` SQLite state database (rusqlite with bundled SQLite; [ADR 0008](docs/adr/0008-rusqlite-with-bundled-sqlite-for-state.md)): migration `001_init.sql` creates packages, grants, profiles, install locks and the active profile; each migration runs in one transaction with the `user_version` bump, so an injected failure rolls back and the active profile stays readable; a corrupt database is quarantined (never deleted) and recreated with the previously active theme restored from a mirrored record; a database from a newer Glint is left untouched (`[INS-002]`).
- `glint-installer` crate with a transactional, content-addressed package store: `install` moves a validated candidate from Glint-owned staging into `store/<sha256>` with one rename and commits it with a journal, so an interrupted install never changes the active profile; installing the same package twice is a no-op; importing never activates unless requested; `remove` is refused while a profile references the package; `recover_pending` (run on every open) rolls back or finishes interrupted operations, cleans staging and trash and rebuilds the index from verified store entries after database recovery. Threat-model rows B1.3, B2.6 and B2.8 updated to partly implemented; bundled SQLite's 260-character database path limit on Windows is recorded as a gap (`[INS-003]`).
- Apply journal, snapshots and crash rollback in `glint-installer`: `apply` records the prior active profile and every planned native preference change with the adapter's snapshot and `canSnapshot`/`canRestore` semantics before changing anything, keeps the old surfaces until the new profile commits, and on failure restores settings in reverse and reports exactly which could not be restored (`GLINT_APPLY_ROLLBACK_INCOMPLETE`); irreversible changes need explicit approval; an interrupted apply leaves the previous theme active, is detected at startup and rolled back with `recover_apply`. Crash tests cover every step; threat-model row B8.3 updated (`[INS-005]`).
- Provenance and same-ID collision policy in `glint-installer`: every installed release records its ADR 0006 origin, source kind and location, registry, Git commit, local path, verified digest, signing status, retrieval time and install path (also in the store entry, so it survives database recovery); installs are classified with `glint-schema`'s `classify_install`, and the same package from another origin (even byte-identical) or a republished version with other bytes is refused with `GLINT_INSTALL_IDENTITY_CONFLICT`, leaving the original intact. ADR 0006 is still *Proposed*; replacing an origin is not implemented. Threat-model rows B1.5 and B8.5 updated (`[INS-004]`).
